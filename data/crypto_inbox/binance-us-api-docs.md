API Key Types Binance.US currently offers three API key types: Exchange API Keys, Custodial Solution API Keys, and Credit Line API Keys. Please read on for more information on the differences and instructions on how to set up your key type. Exchange API Keys can be created in two ways: System generated: Binance.US generates the API key and a secret key. Requests are signed with HMAC SHA256 using the secret key. Self generated: you generate an Ed25519 or RSA key pair in your own environment, keep the private key, and register only the public key with Binance.US. Requests are signed with your private key and verified with the registered public key. There is no secret key. Both kinds of key work on every endpoint and WebSocket API request that requires a signature. See Exchange API Keys for how to create each, and Signature Authentication for how to sign. Timestamp parameters are rejected if they are before 2017-01-01 (< 1483228800000) or more than 10 seconds in the future. Out-of-range startTime/endTime values are clamped to the valid range. Serious trading is about timing. Networks can be unstable and unreliable, which can lead to requests taking varying amounts of time to reach the servers. With recvWindow, you can specify that the request must be processed within a certain number of milliseconds or be rejected by the server. It is recommended to use a small recvWindow of 5000 or less! The max cannot go beyond 60,000! Signature Authentication For SIGNED endpoints you must percent-encode the request payload before computing the signature. Compute the signature over the already-encoded query string / request body, then append &signature=.... Requests that compute the signature before encoding will be rejected with -1022 INVALID_SIGNATURE. How the signature is computed depends on your key type: System generated (HMAC SHA256): use your secret key as the HMAC key over the payload. The signature is the hex-encoded HMAC SHA256 output. Self generated (Ed25519 or RSA): sign the payload with your private key. For RSA, use SHA-256 with PKCS#1 v1.5 padding. Base64-encode the signature, then percent-encode the base64 string before appending it: base64 output can contain +, / and =, which are reserved characters in a query string or form body. Simple Binary Encoding (SBE) Simple Binary Encoding (SBE) is a binary serialization format for low-latency applications, based on the FIX SBE specification. The Binance.US REST API can return responses encoded in SBE instead of JSON. SBE is supported on the REST API only. The WebSocket API and market data streams return JSON only. Requesting an SBE response Sample request curl -sX GET -H "Accept: application/sbe" -H "X-MBX-SBE: 3:5" 'https://api.binance.us/api/v3/exchangeInfo?symbol=BTCUSD' The Accept header must include application/sbe. Provide the schema ID and version in the X-MBX-SBE header as <ID>:<VERSION>, for example 3:5. If the Accept header contains only application/sbe: If the X-MBX-SBE header is missing, malformed, or names a schema that is not supported, the response is an SBE-encoded error. If the Accept header contains both application/sbe and application/json: If the X-MBX-SBE header is missing, malformed, or names a schema that is not supported, the response falls back to JSON. Schema versions Schemas are identified as <ID>:<VERSION>. ID increases when a breaking change is introduced. VERSION is then reset to 0. VERSION increases when a non-breaking change is introduced. ID does not change. When a new schema is released, the previous schema is deprecated, even if the new schema contains only non-breaking changes. A deprecated schema remains usable for at least 6 months after deprecation and is then retired. Retirement dates are announced in advance in the Changelog. Schema Status 3:5 Current 3:4 Deprecated 3:3 Deprecated 3:2 Deprecated Requests that specify a deprecated schema in X-MBX-SBE: receive an X-MBX-SBE-DEPRECATED response header, and are encoded in the highest compatible schema. For example, a request for 3:4 receives a response encoded in 3:5. A decoder for 3:4 is expected to decode 3:5 correctly, as described in the FIX SBE specification's schema extension mechanism. Requests that specify a retired schema are rejected with HTTP 400. Schema files and decoders Download the current schema file: spot_3_5.xml. To generate a decoder, clone and build simple-binary-encoding, then run the SbeTool code generator against the schema file. Encoding notes Decimal fields are encoded as two separate primitive fields, a mantissa and an exponent, to keep payloads small. The mbx:exponent attribute in the schema points from each mantissa field to its exponent field. Timestamps in SBE responses are in microseconds. JSON responses use milliseconds. Each enum includes a NonRepresentable value. Receiving it means the response contains data that your schema version cannot represent; use the latest schema to see it. The schema file includes mbx:jsonPath, mbx:jsonValue and mbx:defaultJsonValue attributes that map each field to its equivalent in the JSON response. Error Responses Error Responses { "code":-1121, "msg":"Invalid symbol." } Errors consist of two parts: an error code and a message. Codes are universal, but messages can vary. Here is the error JSON payload: HTTP Errors HTTP 4XX return codes are used for malformed requests; the issue is on the sender's side. HTTP 403 return code is used when the WAF (Web Application Firewall) Limit has been violated. HTTP 409 return code is used when a cancelReplace order partially succeeds. (i.e. if the cancellation of the order fails but the new order placement succeeds.) HTTP 429 return code is used when breaking a request rate limit. HTTP 418 return code is used when an IP has been auto-banned for continuing to send requests after receiving 429 codes. HTTP 5XX return codes are used for internal errors; the issue is on Binance's side. It is important to NOT treat this as a failure operation; the execution status is UNKNOWN and could have been a success. They are identical to the base endpoint in functionality, behavior and rate limits, and may offer better performance because requests pass through fewer infrastructure layers. You can use them if you experience issues with the base endpoint. All endpoints return either a JSON object or array. Data is returned in ascending order: oldest first, newest last. All times for the fields of staking, referrals, airdrops, etc. are in milliseconds. Making Requests For GET endpoints, parameters must be sent as a query string. For POST, PUT, and DELETE endpoints, the parameters may be sent as a query string or in the request body with content type application/x-www-form-urlencoded. Data Sources(REST) The API system is asynchronous, so some delay in the response is normal. Each endpoint has a data source indicating where the data is being retrieved, and thus which endpoints have the most up-to-date response. These are the three sources ordered from the most up-to-date response to the one with potential delays in updates: Matching Engine - the data is from the matching engine Memory - the data is from a server's local or external memory Database - the data is taken directly from a database Some endpoints can have more than one data source(e.g. Memory => Database). This means that the endpoint will check the first data source. If it cannot find the value it's looking for it will check the next one etc. API Terminology These terms will be used throughout the documentation, so it is recommended that you read them to enhance your understanding of the API (especially for new users). Base asset refers to the asset that is the quantity of a symbol; for the symbol BTCUSDT, BTC would be the base asset. Quote asset refers to the asset that is the price of a symbol; for the symbol BTCUSDT, USDT would be the quote asset. IP Limits(REST) Every request will contain an X-MBX-USED-WEIGHT-(intervalNum)(intervalLetter) header which has the currently used weight for the IP of all request rate limiters defined. Every successful order will contain an X-MBX-ORDER-COUNT-(intervalNum)(intervalLetter) header which has the current order count for the IP of all order rate limiters defined. Rejected/unsuccessful orders are not guaranteed to have a X-MBX-ORDER-COUNT-** header in the response. When a 429 is received, it's your obligation as an API user/trader to back off and not spam the API. Repeatedly violating rate limits and/or failing to back off after receiving 429s will result in an automated IP ban (HTTP status 418). IP bans are tracked and scale in duration for repeat offenders, from 2 minutes to 3 days. A Retry-After header is sent with a 418 or 429 response and will give the number of seconds required to wait to prevent a ban (for a 418) or until the ban is over (for a 429). The limits on the API are based on the IPs, not the API keys. The RAW_REQUESTS rate limit is 300,000 per 5 minutes for order placement and cancellation endpoints. Order Rate Limits(REST) Every successful order response will contain an X-MBX-ORDER-COUNT-(intervalNum)(intervalLetter) header which has the current order count for the account for all order rate limiters defined. Rejected/unsuccessful orders are not guaranteed to have a X-MBX-ORDER-COUNT-** header in the response. The order rate limit is counted against each account.
